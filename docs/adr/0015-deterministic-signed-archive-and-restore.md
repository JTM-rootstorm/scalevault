# ADR 0015: Deterministic signed archive and restore

- Status: Accepted
- Date: 2026-08-09
- Supersedes: None
- Extends: ADR 0003, ADR 0007, and ADR 0009

## Context

Milestone 6 turns the private Forgejo target from a deployment placeholder into
an independently verifiable recovery archive. The existing export-manifest-v1
schema describes file hashes and an event range, but does not freeze snapshot
encoding, signing trust, crash reconciliation, restore ordering, or resource
limits. Those details must be deterministic before an exporter can become the
archive's only writer.

## Decision

### Archive format and deterministic inputs

The first runnable archive contract is `scalevault-archive-v1`. An archive batch
contains canonical JSON events and projections, a deterministic recovery
snapshot, checked-in copies of the schemas used by the batch, and one canonical
manifest. Paths use only normalized relative POSIX components from a closed
layout; symlinks, hard links, special files, absolute paths, empty components,
and `.` or `..` components are forbidden.

Event order is the committed `memory_events.sequence`. Projection collections
and snapshot tables sort by documented primary-key tuples. JSON uses the RFC
8785 implementation and normalization rules accepted by ADR 0009. The batch
timestamp is the normalized `created_at` of the last included event rather than
the exporter wall clock. The exporter version, schema bytes, compression
parameters, event range, and source high-water mark are explicit inputs.
Repeating an export from the same committed database prefix therefore produces
the same archive files, manifest bytes, Git tree, message, author time, and
committer time.

The snapshot is deterministic CBOR using canonical map ordering, shortest
integer and length encodings, definite lengths, and no floats, tags, or
indefinite values. Zstandard compression uses a checked-in parameter profile,
includes content size and checksum, and excludes dictionaries until a future
version identifies their exact bytes. Restore applies strict compressed and
decompressed size limits before allocation.

The snapshot contains the versioned recovery rows required to reconstruct the
canonical tenant identities, lineages, subjects, immutable events, current
semantic projections, selection decisions, command receipts, ingress audit
rows, and external content-key references at its high-water sequence. It
excludes credential material, key bytes, outbox leases, embeddings, search
indexes, exporter checkpoints, Git credentials, and deployment configuration.
Later event files extend the snapshot in sequence order. Derived projections
and embeddings may be rebuilt and are never trusted over validated events.

### Manifest chain and writer election

The new export manifest version records the archive format, source high-water
sequence, event range and count, previous manifest hash, snapshot path and
high-water sequence when present, sorted per-file hashes, schema identities,
exporter version, deterministic export timestamp, and nullable PostgreSQL
timeline metadata. The containing Git commit SHA remains absent or null to
avoid a circular hash; PostgreSQL records it in the checkpoint.

One exporter holds the existing target-scoped PostgreSQL advisory lock from
source-prefix selection through checkpoint reconciliation. It writes into a
dedicated worktree below `/mnt/memory`, verifies every generated byte, creates
one commit, verifies the commit and manifest again, and only then pushes. A
crash after commit but before checkpoint update is reconciled by manifest hash
and exact parent/tree/message identity. Published commits are never amended.

### Signing and trust anchors

Every archive commit is signed with a dedicated Ed25519 SSH signing key owned
only by the exporter service account. The signing key is distinct from the
Forgejo transport key and from content-encryption keys. Git signing is invoked
with fixed arguments and isolated configuration. The trusted public key and
allowed signer identity are pinned in root-controlled operator configuration,
not learned from the archive being verified.

Restore verifies the complete first-parent commit chain, every commit
signature, the manifest hash chain, exact event range continuity, every file
hash, every JSON schema, event canonical bytes and hashes, snapshot encoding,
and the snapshot/event boundary before opening a database transaction. Missing
keys, unsigned commits, unknown formats, gaps, overlaps, extra files, altered
bytes, decompression limit violations, or a dirty destination fail closed.

### Restore transaction

Restore targets a freshly migrated, otherwise empty database or an explicit
disposable recovery database. It never overlays an active canonical node.
Identity and immutable recovery rows are loaded in a fixed dependency order;
events after the snapshot are reduced through the accepted replay path. The
restored canonical aggregate bytes and final high-water sequence must match the
archive. Credentials, service bindings intended for live authentication,
embeddings, and runnable workers are provisioned separately after operator
review.

## Consequences

- Determinism applies to recovery content and signed Git objects, not to remote
  transport timing or Forgejo availability.
- The exporter needs direct runtime dependencies for canonical CBOR and
  Zstandard plus a narrow fixed-argument Git process seam.
- Archive verification is meaningful without trusting Forgejo, a worktree, or
  PostgreSQL checkpoint state in isolation.
- Recovery archives can contain private canonical material and therefore remain
  under the same controlled storage and disclosure boundary as the Memory Node.
