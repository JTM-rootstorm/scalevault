# ADR 0017: Sealed canonical memory content

- Status: Accepted
- Date: 2026-08-09
- Supersedes: None
- Extends: ADR 0005, ADR 0007, ADR 0008, ADR 0009, and ADR 0013

## Context

The initial schema reserves `content_protection`, `content_key_id`, and external
content-key lifecycle metadata, but accepted events and projections still store
the statement, rationale, interpretation limits, evidence summaries, and
metadata as plaintext. Creation paths therefore correctly force `plaintext`.
Changing only the flag would provide no confidentiality and would make hard
forget claims misleading.

Milestone 6 needs optional sealed payload support without rewriting accepted v1
or v2 event bytes or placing encryption keys in PostgreSQL, Git, NFS snapshots,
or the archive.

## Decision

### Versioned sealed representation

Sealed content is additive through a new canonical event/payload and projection
contract version. Existing v1 and v2 events and projection serializers remain
byte-for-byte supported. A sealed memory stores only an allowlisted safe summary
outside its encrypted envelope. The statement, reason to remember,
interpretation limits, evidence text, and content-bearing metadata are absent
from plaintext event, projection, archive, logs, errors, fingerprints, search
documents, and outbox payloads.

The envelope records an algorithm/version identifier, content-key UUID, 96-bit
nonce, ciphertext including authentication tag, canonical AAD hash, and a safe
summary. Ciphertext bytes are Base64 at JSON boundaries and raw bytes in the
database. Unknown algorithms, versions, fields, or missing keys fail closed.
Plaintext v1/v2 representations are never relabelled as sealed.

### Encryption and key boundary

Each protected memory has an independently destroyable 256-bit data-encryption
key generated by a root-controlled key provider. PostgreSQL stores only the
opaque provider name/reference and lifecycle receipt metadata already modeled
by `memory_content_keys`; it never stores the DEK or a wrapping key.

Encryption uses AES-256-GCM with a fresh random 96-bit nonce for every created
or revised sealed after-image. Canonical versioned AAD binds tenant, lineage,
branch, memory, content-key, revision, event identity, schema version, payload
version, and algorithm. A nonce may never repeat for one DEK. Key lookup,
encryption, and decryption occur only in a narrow provider adapter; missing or
ambiguous key material never downgrades to plaintext.

Sensitivity four requires sealing for new canonical writes. Sensitivities zero
and one remain plaintext-capable. Sensitivities two and three may be sealed by
an explicit authorized caller or policy outcome; they are not automatically
upgraded in this milestone. GitHub ingress is sensitivity zero only and can
never submit or request a sealed envelope because its plaintext has already
crossed the GitHub disclosure boundary.

### Search and reads

The safe summary is separately reviewed, bounded, and treated as potentially
disclosive. Eligibility and sensitivity authorization are checked before key
access. An authorized read may decrypt and validate the envelope, then expose
the same semantic read shape as a plaintext memory. An unauthorized or
key-unavailable read does not reveal ciphertext, nonce, tag, key reference,
plaintext length, or crypto exception details. Sealed content is excluded from
lexical and embedding input unless an authorized, local-only indexing profile
is introduced by a later ADR.

### Hard forget

Hard forget requests key destruction through the provider, records only a safe
provider receipt hash and timestamp, removes searchable derivatives and any
ephemeral plaintext, changes the projection to
`cryptographically_erased`, and then appends `payload_purge_completed` through
the accepted lifecycle. A destroyed or unavailable key makes archived
ciphertext unrecoverable but does not promise erasure from unknown plaintext
copies created before protection or by an authorized reader.

### Archive and restore

Archive export copies the already-sealed canonical envelope and external key
reference deterministically; it never decrypts and re-encrypts content.
Restore validates envelope structure and AAD binding without requiring the key.
Content becomes readable only if the separately restored key provider still
holds the matching DEK. Key bytes and provider credentials are never part of an
archive or database snapshot.

## Consequences

- Implementing sealed content requires a migration, new schemas, new reducers,
  storage types, provider interfaces, and compatibility tests; the reserved v1
  columns alone are insufficient.
- `cryptography` becomes a direct runtime dependency rather than a transitive
  implementation accident.
- Safe-summary quality is part of the privacy boundary and cannot be generated
  from sensitive plaintext by an unreviewed remote service.
- Tests must prove that a plaintext canary is absent from database event and
  projection rows, archives, logs, errors, and derivative jobs.
